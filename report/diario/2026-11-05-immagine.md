# 2026-11-05 — App: Dockerfile e immagine unica

**Chi:** Francesco · **Fase:** F2 · **Durata:** 1,5 h · **Issue:** #27

## Cosa abbiamo fatto

- `app/Dockerfile`: una sola immagine per API e worker (D0012). Cosa fa il processo lo decidono `MODE` e `ROLE`.
- `app/.dockerignore`: restano fuori test, dipendenze di sviluppo e file locali.
- Nuovo job «Immagine» nella CI (`.github/workflows/controlli.yml`): costruisce l'immagine su un runner amd64 e su uno arm64 e la avvia nei tre modi (`sync`, `async` API, `async` worker). Controlla che risponda e che il processo 1 sia `uvicorn`.

## Perché

- **`python:3.12-slim`:** la stessa versione di Python della CI. I pacchetti si installano già compilati, senza compilatori nell'immagine.
- **Base fissata con l'hash dell'indice multi-architettura** (`sha256:e695ab18…`): la base non cambia quando esce una nuova patch, ed è la stessa su arm64 e amd64.
- **`CMD` in forma exec, un solo processo:** uvicorn è il processo 1 e riceve direttamente `SIGKILL` e `SIGSTOP` inviati dal nodo (D0016). Con una shell davanti, `SIGSTOP` congelerebbe la shell e non l'API, e F7 non misurerebbe nulla.
- **Bytecode compilato durante la build:** dopo un crash il container riparte senza ricompilare (tempo di riavvio, capitolo delle previsioni).
- **Utente non root** (`uid 10001`) e `PYTHONUNBUFFERED=1`, così i log escono subito.
- **Due architetture:** in locale si costruisce solo arm64, il Mac di Gianmarco su cui si misura (D0013), e si carica in kind. Nella CI si costruiscono amd64 (le istanze `m5` di AWS) e arm64, ognuna su un runner nativo. L'immagine unica con le due architetture si crea quando servirà un registry per AWS (M3b).
- **Tag `kintsugi:<hash del commit>`**, mai `latest`: il run salva l'hash del commit in `meta.json`, quindi ogni misura si collega all'immagine esatta.

## Comandi e configurazione

```bash
# locale (arm64) e caricamento in kind
docker build -t kintsugi:$(git rev-parse --short HEAD) app
kind load docker-image kintsugi:$(git rev-parse --short HEAD) --name kintsugi

# avvio
docker run --rm -p 8000:8000 -e MODE=sync kintsugi:<hash>
docker run --rm -p 8000:8000 -e MODE=async -e ROLE=worker kintsugi:<hash>
```

Prove sul Mac di Francesco (Docker Desktop, server 29.9.2, 5 CPU e 5 GB assegnati). Le prove sulle sonde usano il codice della PR #53, non ancora in `main`.

| Avvio nei tre modi, con database e broker spenti | `/healthz` e `/readyz` rispondono 200 in tutti e tre |
| Processo 1 del container | `uvicorn`, senza shell; utente `kintsugi` |
| Dall'avvio del container alla prima risposta (5 prove) | 0,57–0,87 s |

Il tempo di avvio misurato riguarda solo il processo, non il riavvio in Kubernetes, a cui si aggiungono i tempi del kubelet. È un dato di sviluppo, non una misura: le previsioni restano quelle del tag `m1`.

A fine prova le immagini di prova sono state rimosse dal Docker locale e dai nodi di kind.

## Problemi e soluzioni

- **La prima build sembrava bloccata:** Docker si era appena avviato e il primo download dell'immagine di base non partiva. Dopo una `docker pull` esplicita, la build dura 15 s.
- **Build per due architetture in locale:** Docker Desktop con l'archivio di immagini classico (`overlay2`) la rifiuta: `Multi-platform build is not supported for the docker driver`. Si può risolvere attivando l'archivio containerd in Docker Desktop, ma bisognerebbe cambiare anche il Mac delle misure. La verifica delle due architetture è quindi affidata alla CI.

## Limiti dello strumento emersi

- **Docker Desktop (archivio di immagini classico):** non costruisce né conserva in locale un'immagine con più architetture. Nessun impatto sulle misure: in locale si usa solo arm64.
