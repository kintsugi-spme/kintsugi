# 2026-11-26 — JMeter a ritmo costante (W1, W3)

**Chi:** Francesco · **Fase:** F4 · **Durata:** 3 h · **Issue:** #116 · **PR:** vedi `registro.md`

## Cosa e perché

`harness/jmeter/costante.jmx` è il piano di JMeter 5.6.3 per i carichi costanti: Open Model Thread Group con arrivi regolari (`even_arrivals`), poi una pausa lunga quanto il timeout perché le ultime richieste finiscano. `harness/jmeter/carico.py` lo lancia senza interfaccia con ritmo, durata, indirizzo e timeout (`tempi.timeout_client_s`) e converte i risultati in `client.csv` con le colonne di sempre, così l'analisi non cambia. Una connessione nuova per ogni ordine (D0020): il Service sceglie la copia dell'API alla connessione. Memoria di JMeter fissata a 512 MiB.

## Risultato

Sul Mac da 8 GB, kind v1.37.0, V2 dopo `make reset VERSIONE=v2`, tempo di servizio 0,05 s. Criterio della #83: 50 ordini/s per 180 s, `SIGKILL` a una copia dell'API dopo 60 s (`arresto.py`).

| | |
|---|---|
| Ordini | 9000, tutti con un identificativo diverso; 8989 × `201`, 11 errori durante il guasto |
| Ritmo (`analysis/ritmo.py --ritmo 50`) | medio 50,05/s (+0,1 %); finestra peggiore +2,0 %; codice 0 |
| Fermo (`analysis/fermo.py`) | 0,667 s |
| Categorie (`analysis/categorie.py`, db.csv esportato a mano) | 8989 completati in tempo, 11 falliti, 0 persi, 0 doppi |
| Ordini ricevuti da ogni copia (log dell'API) | 2856, 3159, 2974 |
| CPU di JMeter (ogni 5 s) | mediana 5,9 % di un core, massimo 29,6 % |

```bash
cd deploy/k8s && make v2 && make reset VERSIONE=v2
python3 harness/jmeter/carico.py --ritmo 50 --durata 180 --uscita <cartella>/client.csv
python3 harness/faults/arresto.py --cartella <cartella> --selettore app=api      # dopo 60 s
python3 analysis/ritmo.py <cartella> --ritmo 50
```

## Problemi e limiti

- **Raffica all'avvio.** JMeter parte con qualche istante di ritardo e recupera mandando insieme le richieste arretrate. Con l'identificativo generato da uno script Groovy (compilato al primo ordine) nel primo secondo partivano 80 richieste invece di 50, la prima finestra di 10 s era a +6,4 % e `ritmo.py` scartava il run. Con la funzione `${__UUID()}` di JMeter: 58 nel primo secondo, prima finestra a +1,6 %, run valido. Il resto della raffica è l'avvio di Java; nei run della campagna cade nel minuto di riscaldamento.
- **Un minuto perso a fine test.** Finito il test, JMeter 5.6.3 restava acceso circa 60 s prima di uscire (una prova di 8 s durava 69 s): su 220 run sarebbero circa 3,5 ore. Con la proprietà `jmeterengine.force.system.exit=true` esce subito (9,5 s), con tutti i risultati scritti.
